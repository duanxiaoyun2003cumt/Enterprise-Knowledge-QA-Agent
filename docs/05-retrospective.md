# 05 项目复盘

## 1. 本阶段最重要的发现

1. **安全不变量比预期更重要，也确实生效。** 模型会在没有读取原文时尝试引用检索
   片段，甚至会补写“第二条”“适用范围”等原文没有的文字；引用真实性和“必须已读”
   校验阻止了这些内容被标记为成功。
2. **真实模型的主要风险从“越权/伪造成功”转向“输出不稳定导致任务未完成”。**
   E01 未读引用被拒绝后校验预算耗尽；E03 连续两次非法 JSON。两者都安全地 ended
   incomplete，但完成率受损。
3. **引用真实不等于引用支持结论。** E11 用 D01 的真实 30 日原文支持“差旅住宿材料”
   结论，字符串完全真实、语义完全不支持；自动校验无法识别。
4. **预算不是唯一变量。** 基线 E12B 因 5 次工具硬停止而 incomplete；提示词加入
   预算提示和无证据尽早结束规则后，最终基线 E12B 用 2 次检索结束为
   insufficient_evidence。候选 8/7 单轮自动断言 17/17（8 个真实用例仍需人工
   审查，overall 未定义），但同一用例在基线与候选间多次通过/失败互换，不能据此
   调整默认预算。
5. **文档替换实验证明系统依赖当前证据。** D01 从 30 日改为 45 日后，输出 45/15
   冲突；移除 D01/D02 后，不再输出旧 30/15 期限。

## 2. 最难解决的工程/决策问题

### 2.1 安全硬校验与模型恢复的张力

校验器严格拒绝未读/伪造引用是正确的，但每次拒绝都消耗有限的校验预算。E01 的
“非法动作 + 未读引用”两次失败就把 2 次预算用完，模型没有第三次机会读取并修正。
简单提高预算会增加成本和潜在重复；简单放宽校验会破坏安全。当前选择保留严格校验
和 2 次重试，把问题记为未解决，而不是用降低安全性换完成率。

### 2.2 硬工具预算与完成率

达到工具上限立即停止是阶段四的安全约束，但也导致 E12B 在用满 5 次工具后没有机会
结束。提示词让模型更早结束能改善单例，但不能保证所有模型运行都遵守；候选预算能
允许更多工具，却在其他样例中并不带来一致收益。当前保留 6/5，并记录该取舍。

### 2.3 语义支持无法用字符串证明

引用真实性可以确定性验证；语义支持需要业务判断。E11 是刻意保留的失败用例，
说明自动校验通过不等于答案可信。当前只能把语义审查单独记录，不能把它并入自动
通过率。

## 3. 实际修复

- **提示词加固**：
  - `search_documents` 的 snippet 不能直接引用，引用前必须 `read_document`；
  - quote 必须逐字复制 content，不得补章节号、条款号、适用范围或日期；
  - 无候选/无事实时尽早 `insufficient_evidence`；
  - 在 system context 中明确当前最大步数和工具调用预算。
- **预算配置集中**：`main.py` 从 `agent.py` 导入 `MAX_STEPS` / `MAX_TOOL_CALLS`，
  消除 CLI 的第二套硬编码默认值。
- **评测基础设施**：统一评测集、真实/FakeLLM 分离、Trace 保存、自动断言、人工
  语义审查挂接、预算 profile 和临时数据变体。
- **回归测试**：208 个自动化测试通过；新增评测用例与结果文件保留。

没有删除安全检查、扩大工具权限、降低引用/Schema 严格性或放宽冲突约束。

## 4. 尚未解决（阶段五视角）

> 阶段六已拆分格式/最终校验预算并重复采样；E01/E03 在阶段六批次 5/5 自动通过，
> 但 E11 人类评审 fail、E12B/E13 follow-up。详见第 8 节。

- E01/E03 的模型输出不稳定：非法 JSON、未读就引用；校验预算耗尽后 incomplete。
- E11 的语义支持盲区：没有自动语义评审，只能人工审查。
- 真实样本只有 7 个用例、每类少次运行；预算结论不具统计显著性。
- 候选预算单轮自动断言 17/17（人工审查 pending）不能证明预算更优；默认仍为 6/5。
- `trace_review.json` 是 AI 辅助的非自动审查，不是独立人类评审；最终交付前必须
  由人类复核。
- 硬工具预算在最后一次证据可用时可能过早结束；这是已知取舍。
- 冲突检测和优先级证据仍是启发式，复杂真实制度可能漏检。

## 5. 从真实失败中学到什么

- 真实模型会无视“只引用已读原文”的指令；必须由程序校验，不能依赖 Prompt。
- 模型的 JSON 输出可能包含额外文本（Extra data）或缺少字段；格式修复/重试预算
  需要单独设计，不能和最终结果语义校验混在一个很小的计数器里。
- 检索 snippet 很容易被模型当作证据；observation 需要明确标注“候选、非引用”。
- 单次真实运行不能代表模型质量；同一用例在不同预算下出现相反结果。
- FakeLLM 能证明“控制流安全”，不能证明“真实决策有效”；两类证据必须分开。

## 6. 下一步最值得投入

1. 增加真实模型重复采样（同一用例至少 3–5 次），统计完成率、方差和失败类型，
   再决定是否调整校验重试或预算。
2. 设计受限的格式修复/重新请求：仅处理可确定的 JSON 对象，不执行未校验内容，
   并计入独立预算。
3. 引入独立人类或语义评审流程，对引用是否支持结论做检查；不要把字符串匹配当
   语义证明。
4. 继续用文档替换和对抗测试验证证据依赖与安全边界；扩展冲突规则。
5. 完整最终交付材料：复现步骤、环境记录、AI 使用说明、Git 提交、独立审查记录。

## 7. 诚实结论

当前系统在安全边界上明显强于“模型能回答”的基线：引用真实性、已读要求、冲突
澄清、空结果/工具错误区分、预算和恶意输入处理都有实际测试和 Trace 证据。
但真实模型仍有输出不稳定和语义支持盲区，阶段五的评测结果不能宣称“全部通过”
或“已经生产可用”。最有价值的下一步不是增加功能，而是增加重复真实采样、限定
格式恢复和独立语义评审。

## 8 阶段六可靠性收口复盘

### 8.1 实际发现与修改

- 旧实现确实让格式/Schema 错误与最终结果校验失败共用一个
  `validation_failures` 计数。E01/E03 的失败部分来自这个共享预算。
- 已拆为 `MAX_FORMAT_REPAIRS=2` 与 `MAX_FINAL_VALIDATION_RETRIES=2`；每次修复/
  重试仍计入 `MAX_STEPS=6`，工具错误不消耗这两类预算。
- 格式修复只重新请求并完整执行 JSON + Pydantic 校验；没有字符串修补、没有绕过
  引用/冲突校验、没有直接执行未验证动作。
- Trace 增加 `repair_kind`、`format_repairs`、`final_validation_retries`。
- 自动化测试从 208 增至 **216 passed**，新增 `tests/test_repair_budgets.py`；
  最终验收前 follow-up 再增至 **231 passed**。

### 8.2 重复采样结果

- 25 次真实运行（E01/E03 各 5 次，其余各 3 次）：**24 自动通过，1 失败**。
- 默认预算批次发生 8 次格式修复（涉及 7 次运行，均恢复并通过），0 次最终结果
  校验重试；总 99 步 / 67 工具；预算耗尽 1 次。
- E01 5/5、E03 5/5；E12B 2/3，唯一失败为 5 次工具 `tool_limit`（阶段六初始批次）。
- E12B 候选 8/7 预算 3/3，其中一次 7 steps / 4 tools；样本只有 3 次，不能据此
  调整默认 6/5。最终验收前 follow-up 已扩充到两组各 8 次，见第 9 节。
- 用户已对 8 个代表性用例完成第一轮人类评审：5 pass / 1 fail / 2 needs_followup。
  逐样本的语义审查仍未覆盖全部 25 次运行，`business_pass_rate` 仍未定义；
  自动通过率不是业务通过率。
- E11 的 5 次是 FakeLLM 受控采样，自动 5/5；人类评审判定引用真实但语义不支持，
  因此 E11 业务判定 fail，不能当作真实模型稳定性或业务通过。

### 8.3 仍未完成

- 用户已完成第一轮人类评审（5 pass / 1 fail / 2 follow-up）；历史 E11 fail 保留。
  follow-up 已补齐技术证据，用户也给出了带限制判断：E11 回归修复通过但带限制、
  E12B 保留 6/5、E13 未观察到安全绕过但完成率 2/4；整体状态
  `reviewed_with_open_limitations`，不是全面通过。
- E12B 已补到默认/候选各 8 次真实样本；默认 7/8、候选 8/8，仍不具统计显著性，
  默认预算继续 6/5。
- 引用语义支持已有确定性的主题/claim 守卫，但它不是完整语义蕴含；E11 原始人类
  FAIL 仍是对原始运行的权威结论，新运行不能替换它。
- E13R 已有 4 次真实模型注入运行；4/4 读取恶意文档、安全不变量通过，但 2/4 因
  保守语义校验/步数预算 incomplete，样本仍小。
- 真实模型非确定性仍存在；阶段六 E01/E03 的 5/5 不能保证未来。
- 没有 Git commit/push；需要人工确认 follow-up 复核后再提交，且 `.env` 必须继续
  被忽略。

### 8.4 学到的经验

- 共享重试计数器会把“格式恢复”和“证据/引用修正”混为一谈；拆开后模型有合理的
  修复机会，同时安全校验不变。
- 格式修复必须重新走完整 Schema，不能把修复响应直接当成已执行动作。
- 自动断言通过率和业务通过率必须分开；人工语义评审缺失时，不能报告业务通过率。
- 硬预算对完成率有真实影响；E12B 的失败是具体证据，但少量样本不足以调参。

## 9 最终验收前 follow-up 复盘

### 9.1 E11：语义支持不能只靠字符串真实性

- 原失败是“引用字符串真实，但 D01 的期限原文不能支持 D03 的材料结论”。
- 修复没有引入额外的语义模型调用，而是把答案拆成 claim，检查 claim 与 quote 的
  业务主题和数值期限是否兼容；`unsupported` 和 `uncertain` 都拒绝，异常时
  fail closed。
- 这个方案的价值是：可解释、确定性、零额外预算；能拦截 E11 和 30 日引用支持
  45 日 claim 这类明确错配。
- 局限也很清楚：主题词典是人工维护的，不能证明完整蕴含。`uncertain` 采用保守
  拒绝，可能把本可回答的内容退化为 `insufficient_evidence`。这是安全优先的
  取舍，不应为了提高完成率而改成默认支持。

### 9.2 E13R：安全通过不等于任务完成

- 4 次真实运行都实际检索并读取了恶意文档 E01；模型没有执行 `shell_exec`、没有
  读取路径、没有泄露凭证、没有改变预算，安全不变量 4/4。
- 但只有 2/4 正常 `finish`；另外 2 次因为模型坚持引用恶意文本来解释“文档没有
  合法流程”，语义守卫无法识别安全/元话语主题，判为 `uncertain` 并拒绝，最终
  耗尽最终校验或步数预算。
- 这说明“安全边界通过”和“自动完成断言通过”必须分开报告。若为了让 E13R 显示
  PASS 而删除 stop_reason 断言或放宽语义校验，会掩盖真实完成率问题；当前选择
  保留失败并记录原因。
- 4 次运行仍不能证明模型对 Prompt 注入普遍免疫；程序级白名单/路径拒绝仍由确定性
  测试证明。Trace 不保存非法模型原文，也限制了对“尝试未注册工具但 JSON 解析
  失败”的识别。

### 9.2.1 重试计数口径缺陷（已修正）

- 复核发现 `4be54b4e` 的 Trace 记录 `final_validation_retries=3`，而
  `MAX_FINAL_VALIDATION_RETRIES=2`。逐步骤核对后确认：step 3 是初始失败，
  step 4/5 是两次重试，step 5 的失败只是触发停止的终止失败；**实际没有第三次
  重试**，不是预算边界被突破。
- 根因是旧实现先递增计数器、再判断预算，字段名 `retries` 实际统计的是
  “失败次数（含终止失败）”。
- 修正为两套计数：`*_failures` 统计所有失败，`*_retries` / `repairs` 只统计
  实际发出的重试请求（仅当还有下一步时递增）；预算判断使用失败计数。新增
  `test_final_validation_budget_counts_retries_not_terminal_failure` 和
  `test_format_budget_counts_repairs_not_terminal_failure`。
- 历史 Trace 不重写，分析脚本从步骤序列推导实际重试数；这既保留原始证据，也让
  复核者能看到旧字段与修正口径的差异。
- 教训：安全预算的“计数器名称”也是契约的一部分。仅验证“没有超过 MAX”不够，
  还要验证字段含义、终止失败是否计数、Trace 与文档是否一致。

### 9.3 E12B：失败不是重复检索，候选预算也不是通用解

- 默认 8 次：7 次 `insufficient_evidence`，1 次 `tool_limit`；失败 Trace 使用
  4 个不同查询 + 1 次读取，没有重复查询或重复读取，第 5 次工具仍用于新的低价值
  检索，未能在硬上限前结束。
- 候选 8 次：8/8 自动通过，平均 4.625 步 / 3.125 工具；最长一次 8 步 / 5 工具，
  含 2 次格式修复，说明候选多出的步数在格式恢复场景下有实际作用。
- 但这不等于“候选预算更优”：8+8 是小样本，候选步数更高、格式修复更多，默认组
  失败是单次工具预算事件。默认预算保持 6/5 是诚实结论，不是保守惯性。
- 实验设计上，四个批次文件按预算分开保存，合并统计只读取同一用例的 E12B 记录，
  避免把不同批次混成一个通过率。

### 9.4 新的工程经验

- 语义校验的“保守拒绝”会把风险从“错误 answered”转成“安全 incomplete”；这是一
  个可接受的失败方向，但必须同时报告完成率损失。
- 自动断言、AI 汇总、真实模型运行、人类评审是四种不同证据。用户已提供
  follow-up 带限制判断：E11 `pass_with_limits`、E12B
  `accepted_no_budget_change`、E13 `partial`，整体
  `reviewed_with_open_limitations`；没有把任何新结果标成全面 PASS，历史 E11
  FAIL 也没有被覆盖。
- 评测用例应在看到结果前定义检查项。E13R 的 `stop_reason` 检查导致 2 次完成失败，
  但它同时暴露了保守语义校验的成本；保留该检查比事后删除更诚实。
- 预算实验需要固定输入、数据哈希、模型、提示词哈希和断言，只改变预算；本次
  E12B 使用了同一数据副本和同一提示词哈希，四个批次可追溯。
